Modelado dimensional para BI

Del modelo transaccional al modelo estrella y copo de nieve, aplicado a un caso real de negocio.

¿Por qué un modelo dimensional?

Las bases de datos transaccionales están optimizadas para registrar operaciones. El modelado dimensional las reorganiza para que sea rápido y simple hacer preguntas de negocio.

Modelo transaccional (OLTP)

Optimizado para registrar (insertar, actualizar). Muchas tablas normalizadas, difícil de leer. Prioriza evitar duplicidad de datos.

Ejemplo: sistema de punto de venta.

Modelo dimensional (BI)

Optimizado para consultar y analizar. Pocas tablas, estructura clara (hechos + dimensiones). Prioriza velocidad de consulta y facilidad de uso.

Ejemplo: modelo para el dashboard de ventas.

Modelo estrella (star schema)

Una tabla de hechos central conectada directamente a las tablas de dimensión, sin niveles intermedios.

Ventaja clave: consultas simples (pocos JOIN) y fácil de entender para usuarios de negocio.

Modelo copo de nieve (snowflake schema)

Las dimensiones se normalizan en sub-tablas adicionales, reduciendo la redundancia de datos.

Ventaja: menos redundancia y datos más consistentes. Costo: más tablas y JOINs, consultas algo más lentas.

Estrella vs. copo de nieve: ¿cuál elegir?

CriterioEstrellaCopo de nieve
Complejidad de consultaBaja (JOINs directos)Media-alta (varios niveles)
Redundancia de datosMayorMenor
Velocidad de lecturaMás rápidaAlgo más lenta
Facilidad para usuarios de negocioAltaMedia
Ideal paraDashboards y reportes ágilesModelos con dimensiones muy grandes/complejas

Preguntas que el modelo debe responder

  • ¿Cuáles son los productos más vendidos por sucursal?
  • ¿Cómo varían las ventas por día de la semana?
  • ¿Qué categoría genera más ingresos?
  • ¿Cuál es el ticket promedio por cliente?

Tabla de hechos: Ventas

  • fecha
  • producto_vendido
  • sucursal
  • cliente (si aplica)
  • cantidad
  • precio_unitario
  • total_venta
Dimensiones sugeridas: Dim_Producto, Dim_Sucursal, Dim_Cliente, Dim_Tiempo
